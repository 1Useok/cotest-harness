# 01. 구성 요소별 설계 의도

구성 요소마다 무엇을 막으려는 것인지, 그리고 그 설계가 나온 실행 기록을 적었습니다. 실행별 날짜와 버전은 `02_history.md` 에 있습니다.

## 1. 규칙 파일 (`AGENTS.md`, `CLAUDE.md`)

모든 에이전트가 처음에 읽는 파일입니다. Claude Code 는 `CLAUDE.md` 를 통해 `AGENTS.md` 를 읽고, GPT(Codex)는 `AGENTS.md` 를 읽습니다.

**근거는 기계가 낸 결과뿐입니다.** 모델이 "확인했다"고 말하고 넘어가는 것을 막습니다. 제한 시간 안에 여러 문제를 푸는 조건에서는 사람이 코드를 한 줄씩 검토하는 방식이 성립하지 않으므로, 판정의 근거를 스크립트의 출력으로 한정했습니다.

**테스트를 구현에 맞추지 않고, 고치지 못한 반례는 `known_fail/` 에 남깁니다.** 틀린 구현에 맞춰 기대 출력을 바꾸는 일을 막습니다. 연습 1 에서 고치지 못한 반례를 담을 자리가 없어 임시 폴더를 만들었는데, 그 반례가 있어도 PASS 가 났습니다. 이후 `known_fail/` 이 있으면 판정이 조건부가 되게 했습니다.

**독립 구현은 원문의 문장에 어긋날 때만 수정할 수 있습니다.** 연습 2 에서 독립 구현이 원문 글자를 따라 답안과 다른 출력을 냈고, 구현 에이전트가 독립 구현을 답안 쪽으로 고쳤습니다. 이후 GPT 리뷰가 같은 점을 짚었습니다. 답안에 맞춰 비교 대상을 고치면 비교가 의미를 잃으므로 규칙으로 막았습니다.

**문제에 없는 요구를 만들지 않고, 세부 하나에 15분을 넘기면 멈춥니다.** 연습 1 에서 원문에 없는 정확한 분수 계산을 정답 조건으로 삼아 결정이 3개 더 생겼고, 시간 대부분이 거기에 쓰였습니다.

**정답 규칙을 바꾸는 구현 선택(근사, 상한)은 확신도와 상관없이 사람에게 올립니다.** 연습 1 에서 에이전트가 분모 상한(D19)을 "확신 중간"으로 혼자 정했고, 리뷰에서 그 상한 때문에 경계 근처 값이 틀린다는 것이 드러났습니다.

**판단 기준 4개**는 문제에 명시되지 않은 경우가 "출력 없이 무시"로 기우는 것을 막습니다. 리허설 2 에서 명시되지 않은 경우 9곳 가운데 문제 설계 메모와 같은 처리는 1곳뿐이었던 데서 나왔습니다. 4번 "같은 ID 는 한 번만 반영"은 v7 에서 주문번호의 신규 접수로 좁혔다가, 리허설 3 에서 같은 체결번호에 내용이 다른 체결을 따로 세는 처리가 나와 체결 ID 까지 다시 넓혔습니다.

**사용자에게 보이는 글은 모두 한국어입니다.** 연습 2 에서 첫 결정 카드와 진행 설명이 영어로 나와 판단 속도가 떨어졌습니다.

**`DECISIONS.md` 에는 출력 규칙만 적고, 구현 방법은 `## 구현 메모` 절에 따로 적습니다.** 연습 1 에서 독립 구현도 같은 수치 표현을 지시받아 두 구현이 같은 오답을 냈습니다. 구현 메모 절은 독립 구현에 전달하지 않습니다.

## 2. 절차 6개 (`.claude/skills/`)

| 절차 | 하는 일 | 막는 것 |
|---|---|---|
| `/intake` | 자료 전처리, 타이머 시작, 문제마다 전사·요구사항·엣지 케이스 표·결정 기록 작성, 결정 카드를 한 번에 제시 | 문제의 일부(메일 본문의 정정 등) 누락, 숫자 전사 오류 |
| `/solve pN` | 테스트 작성, 구현, 차등 퍼징, 뮤테이션 테스트, 리뷰, 보고 순서로 진행 | 구현을 먼저 쓰고 테스트를 거기에 맞추는 것 |
| `/probe pN <상황>` | 사람의 "이러면?"을 입력으로 바꿔 두 구현에 넣어 봄 | 사람이 떠올린 경우가 검증에서 빠지는 것 |
| `/ask <질문>` | 파일을 고치지 않고 답만 하는 질문 세션 | 판단에 쓴 보조 질문이 사용 기록에서 빠지는 것 |
| `/finish` | 최종 검증, 조건부 결과의 승인, AI 사용 기록, 제출물 정리 | 검증하지 않은 파일이나 이전 버전의 파일을 제출하는 것 |
| `/explain pN` | 제출 후 답안 설명서 작성 | 제출한 답안을 설명할 일이 생겼을 때 근거가 없는 것 |

`/ask` 는 리허설 2 에서 판단에 쓴 보조 질문 9건이 제출물에 들어가지 않은 것을 확인하고 추가했습니다.

문제가 여럿이면 문제마다 세션 하나가 `/solve` 를 맡아 병렬로 진행합니다. 리허설 1 에서 처음으로 세 세션을 동시에 돌렸습니다.

## 3. GPT(Codex) 지시문 4개 (`prompts/`)

`scripts/codex_ask.sh` 가 빈 디렉터리에 필요한 파일만 넣고 Codex 를 호출합니다. 출력이 `OK:` 로 시작할 때만 성공으로 봅니다.

| 지시문 | 받는 것 | 받지 않는 것 | 목적 |
|---|---|---|---|
| `ambig.md` (모호한 요구사항 탐색) | 문제 원문 | 구현 에이전트의 정리 | 한쪽 모델이 떠올린 빈칸만 결정되는 것을 막음 |
| `alt.md` (독립 구현, 두 번째 입력 생성기) | 원문, 결정 기록(구현 메모 절 제외), 성능 사전의 "큰 입력 모양" 절 | 답안, 기대 출력, 구현 방법 | 한쪽만의 버그, 입력 생성기와 답안이 같은 맹점을 공유하는 경우를 잡음 |
| `cases.md` (기대 출력 교차 검증) | 테스트 케이스의 입력, 원문, 결정 기록 | 기대 출력, 답안 | 구현과 테스트를 같은 모델이 쓰면서 문제를 잘못 읽은 경우를 잡음 |
| `review.md` (코드 리뷰) | 답안, 함정 사전, 성능 사전 전체 | | 재현 입력이 있는 지적만 반영 |

Codex 호출이 실패하면 Claude 하위 에이전트에게 같은 지시문과 같은 파일만 줍니다. 같은 Claude 계열이라 독립성이 약하다는 점은 보고서에 기록합니다. 연습 1 직후의 첫 점검에서 "Codex 가 오류로 끝나도 산출 파일만 있으면 성공으로 처리한다"는 결함이 재현되어, 종료 코드와 산출물을 함께 확인하게 했습니다.

## 4. 검증기 (`scripts/verify.py`)

판정은 세 가지입니다. PASS 는 모든 검사를 실행했고 실패가 없다는 뜻, 조건부는 실패는 없지만 사람이 알고 받아들여야 할 것이 있다는 뜻, 그리고 FAIL 입니다. 처음에는 PASS 와 FAIL 둘뿐이었는데, 연습 1 에서 알려진 오답과 생략된 검사가 있어도 PASS 가 나와 세 단계로 나눴습니다.

검사 항목별로 도입한 이유는 다음과 같습니다.

| 검사 (도입 버전) | 이유 |
|---|---|
| 표준 라이브러리만 사용, 지정 빌드 명령, 경고 0개 | 작업 조건 |
| 기대 출력 교차 검증 (v4) | 같은 모델이 문제를 잘못 읽어 기대 출력과 답안이 함께 틀린 경우를 잡습니다. GPT 가 확인한 비율이 절반보다 낮으면 조건부입니다. 사람의 육안 확인을 대체하기 위해 만들었고, 복사본에서 리허설 1 의 세 문제에 돌리자 44개 가운데 3개가 달랐습니다. 셋 모두 결정 기록에 정해 두지 않은 규칙이었습니다 |
| 엣지 케이스 대응 (v2) | 표가 비어 있어도 조건부입니다(v7). 외부 리뷰에서 빈 엣지 케이스 표가 PASS 라는 지적을 받았습니다 |
| 불변식 체커 | 값을 계산하는 문제는 Python 정수·분수로 다시 계산합니다. 연습 1 에서 두 C++ 구현이 같은 정밀도 오류를 냈습니다 |
| 차등 퍼징 | 고정 seed 600개와 새 seed 400개, 두 입력 생성기를 번갈아 씁니다. 첫 점검에서 고정 seed 만 쓰면 같은 입력만 반복된다는 지적이 있었습니다 |
| 무작위 입력의 치우침 (v3) | 연습 2 에서 무작위 입력의 출력 33% 가 없는 주문번호였고, 체결은 2.7% 였습니다 |
| 중간 규모 차등 테스트 (v7) | 외부 리뷰에서 무작위 입력이 60줄 이하라 수백 줄 이후에만 나타나는 버그가 PASS 라는 지적을 받았습니다 |
| 최대 규모 입력의 시간, 증가율, 메모리 (v3, v5, v6) | CPU 시간으로 재고, 기준을 넘으면 두 번 더 잽니다. 리허설 2 에서 세 세션이 함께 돌아 시간이 부풀어 조건부가 났습니다 |
| 커버리지 (v2) | "확인"으로만 알립니다. 연습 1 에서 알려진 오답을 만드는 바로 그 코드 11줄이 어떤 테스트에서도 실행되지 않았습니다 |
| 뮤테이션 테스트 (v2) | 변형이 0개면 조건부입니다(v7). 외부 리뷰에서 숫자 구분자 `1'000` 이 있으면 변형할 자리가 0곳이 되어 검사가 통째로 무력해진다는 것이 드러났습니다 |
| 알려진 오답 | 고치지 못한 반례를 숨기지 않게 합니다(연습 1) |
| 결정 카드 (v7) | 사람이 답하지 않은 카드를 추천안 그대로 제출하는 것을 막습니다. 두 외부 리뷰가 모두 짚었습니다 |

최종 검증(`final_gate.sh`)은 같은 검증을 돌리고, 처음 읽은 소스 그대로 `submit/` 에 복사합니다. 검증 중에 파일이 바뀌면 FAIL 입니다(v7, 외부 리뷰에서 재현된 결함).

검증기 자체는 셀프 테스트로 확인합니다. `selftest/s1` 예제 문제에 버그 8종(`selftest/mutate.py`)을 하나씩 심어 모두 잡는지, 하네스의 실패 경로 16개(h1\~h16)에서 PASS 가 나오지 않는지를 `scripts/selftest.py` 가 확인합니다.

## 5. 결정 카드 (`templates/FORMATS.md`)

문제에 명시되지 않았고 실무 관례도 갈리는 것을 사람에게 묻는 형식입니다. 한 화면에 들어오는 표 하나이고, 문제당 처음 올리는 카드는 3장까지입니다. 선택지마다 추가 소요 시간(분)을 적고, 선택지 하나는 원문 글자 그대로입니다. 원문이 그 경우를 아예 말하지 않으면 그 선택지를 "원문에 없음: 아무것도 더하지 않는다"로 표기합니다. 답을 기다리지 않고 추천안으로 먼저 진행하고, 답이 다르면 그때 수정합니다.

- **선택지별 추가 시간**: 연습 1 에서 추천과 다른 선택지가 골라졌는데, 카드에는 위험이 "계산이 복잡해진다" 한 줄뿐이었습니다. 그 선택이 큰 정수 구현, 108초 걸리는 답안, 추가 결정 3개로 이어졌습니다.
- **표 하나, 3장까지, 기다리지 않기**: 연습 2 에서 카드마다 12항목이었고 6장 모두 "추천대로"로 끝났습니다. 40분 가운데 24분이 답을 기다린 시간이었습니다.
- **"원문에 없음" 표기**: 외부 리뷰에서 원문이 시킨 것처럼 보인다는 지적을 받고 바꿨습니다.

## 6. 기록과 제출물

이 하네스는 모든 AI 사용을 대화 원본과 모델 이름까지 기록으로 남기는 것을 전제로 합니다. 그래서 기록이 빠지는 경로를 막는 데 공을 많이 들였습니다.

- `log_step.sh`: 단계마다 "누가(모델), 무엇을" 한 줄을 기록하고 커밋합니다. 사람의 답은 반영하기 전에 사람의 파일만 커밋합니다. 연습 2 에서 "[사람]" 커밋에 AI가 고친 코드가 섞였기 때문입니다.
- `collect_logs.py`: 원본 대화 기록을 모으고 목록(파일, 시각, 모델, 해시)을 만듭니다. 응답이 끝날 때마다 다시 모으고, 작업 시간 범위만 모으고, 잠금을 겁니다(v7). 연습 1 에서 대화 내보내기가 앞부분을 빠뜨렸고, 외부 리뷰에서 수집 두 개가 겹치면 서로 지운다는 것이 드러났습니다(동시 40회 중 오류 11회, 수정 후 0회).
- `usage_export.py`: 원본에서 읽기 쉬운 기록(전체, 세션별, 문제별, 사람이 입력한 것, 모델 표)을 자동으로 만듭니다. 리허설 1 에서 세션 4개의 내보내기를 일일이 실행해야 했습니다.
- 보조 질문 수집: VS Code 가 따로 저장하는 보조 질문을 찾아 제출물에 넣습니다. 리허설 2 에서 보조 질문 9건이 제출물에 없었습니다.
- `pack.sh`: 답안, 기록, `SUBMIT_LIST.md` 를 만들고, 이전 버전의 제출 파일과 수집 실패를 눈에 띄게 알립니다(v7). 외부 리뷰에서 최종 검증이 FAIL 이어도 이전 제출 파일을 "문제없음"으로 올린다는 지적을 받았습니다.
- `HARNESS.md`: 작업 방식을 설명하는 한 장짜리 문서(1인칭)입니다.

사람이 실제로 입력한 것은 `02_human_inputs.md` 에 자동 추출한 그대로 들어갑니다. 리허설 1 에서는 `/solve p1`, `추천대로`, `확인` 같은 11줄이 전부였습니다.

## 7. 진행 현황판 (`scripts/board.sh`)

문제별 단계, 작업 시간과 사람 답 대기 시간, 마지막 판정, 교차 검증과 뮤테이션 테스트의 수, "지금 사람이 할 일"을 한 화면에 보여 줍니다. 별도 터미널에 띄워 둡니다.

연습 1 직후 점검에서 "과정이 눈에 보이지 않는다"는 문제가 기록됐습니다(첫 점검의 교차 검토). 현재 상태를 알려면 대화를 거슬러 읽거나 파일 여섯 개를 열어야 했습니다.

v7 에서는 병렬로 풀 때 시간을 문제 수로 나눠 "예산 초과"로 세 세션을 모두 멈추게 하던 동작을 알림으로 바꿨습니다. 맨 위에 "제출 준비(/finish)를 시작할 시각"이 항상 보입니다.

## 8. 그 밖의 장치

- **자료 전처리 (`inbox_scan.py`)**: 압축 파일, 워드 문서, 메일 본문에서 일부를 놓치는 것을 막습니다. 같은 이름의 첨부, tar, 워드 수식 경고(v7), 윈도우식 zip 의 역슬래시 경로를 처리합니다. 외부 리뷰에서 같은 이름의 첨부가 서로 덮어쓴다는 것이, 리허설 3 준비 중에 윈도우식 zip 을 폴더로 풀지 못한다는 것이 드러났습니다.
- **원문 대조 (`transcribe_check.py`, v4)**: 잘못 옮긴 숫자 하나로 모든 구현이 함께 틀리는 것을 막습니다. 리허설 1 에서는 전사한 숫자를 원본과 대조하는 일이 사람에게 요청되는 구조였고, 제한 시간 안에서는 수행되지 않았습니다. 그래서 자동 대조로 바꿨습니다. 외부 리뷰에서는 `이하→미만`, `B→S` 를 "같다"고 판정한다는 것이 드러나 v7 에서 강화했습니다.
- **입력 파싱 기본 규칙 D0 (v4)**: 세션마다 공백과 숫자 처리가 달라지는 것을 막습니다. 리허설 1 에서 한 문제는 `-0` 을 거부하고 다른 문제는 받았습니다. 한 문제는 탭을 받았다가 독립 구현과 30건이 달라 고쳤습니다.
- **과제 안내문의 제한 (`limits.conf`, v7)**: 안내문의 메모리 제한을 넘는 답안이 PASS 가 되는 것을 막습니다. 외부 리뷰에서 256MB 제한을 넘는 310MB 답안이 PASS 였습니다.
- **모델 이름 자동 기록 (v4)과 모델 전환 `models.sh` (v6)**: 대화 기록과 다른 모델 이름을 적는 것을 막습니다. `models.sh` 는 설정과 함께 실제로 쓰인 모델을 대화 기록에서 읽어 보여 줍니다. 리허설 1 에서 구현 에이전트가 Codex 모델 이름을 "gpt-5 계열"로 추정해 적었다가 고쳤습니다.
