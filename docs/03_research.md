# 03. 사전 조사: 함정 사전과 성능 사전

에이전트가 코드를 쓰기 전에 참고할 지식 기반 두 가지를 미리 만들었습니다. 모델의 사전 지식에만 기대면 그럴듯하지만 실무와 다른 구현이 나오기 쉽기 때문입니다. 진행 중에는 에이전트가 요구사항 정리와 리뷰 때 필요한 절만 읽습니다.

| 사전 | 다루는 질문 | 쓰이는 곳 |
|---|---|---|
| 도메인 함정 사전 (`knowledge/TRAPS.md`) | 입력 형식은 정상인데 순서나 의미가 까다로운 경우, 무엇을 출력해야 맞는가 | 엣지 케이스 표의 재료, GPT 코드 리뷰의 체크리스트, `/probe` |
| 성능 사전 (`knowledge/PERF.md`) | 그럴듯한 구현이 어떤 입력에서 느려지는가, 맞는 출력을 제때 내는가 | 효율 계획의 자료구조 선택, 최악 입력 설계, 리뷰 |

### Reddit 조사: Aside 연결

Reddit 조사에서는 문제가 하나 있었습니다. Claude 의 기본 웹 도구(검색, 페이지 열기, 내장 브라우저)가 모두 Reddit 에서 차단됐습니다.

우회 사이트를 쓰는 대신, 로그인된 브라우저를 직접 구동하는 에이전트인 Aside 를 Claude Code 에 MCP 서버로 연결했습니다. Claude Code 가 Aside 에 읽을 스레드를 맡기고, Aside 가 읽고 요약한 결과를 받아 추리는 방식입니다. 조사는 읽기 전용으로 했고 글쓰기·투표·가입은 하지 않았습니다.

- **1차 (11-13)**: 세션 두 개를 나란히 돌려 주문 관리·실행 사례(스레드 52개)와 호가창·매칭 구현 리뷰(스레드 56개), 모두 108개를 읽었습니다. 요청 횟수 제한에 걸려 8개는 열지 못했습니다. 새 항목은 T100\~T127(28개)입니다.
- **2차 (11-13)**: 1차에서 열지 못한 8개를 포함해 스레드 59개를 읽었습니다. 새 항목은 T198\~T203(6개)이고, 나머지는 기존 항목을 다시 뒷받침했습니다.

Reddit 에서 나온 새 항목은 모두 34개입니다. 찾으려 했지만 Reddit 에서 사례가 나오지 않은 주제(재접속 뒤 같은 체결 통보의 중복 수신, 가격 0 주문, 중복 주문번호, 이미 체결된 주문의 취소, 빈 호가창의 시장가)는 규격서와 `[I]` 코드에서 이미 넣어 두었습니다.

### 선별 기준

표준 입력을 읽어 표준 출력에 쓰는 OMS 문제에 적용할 수 있는 것만 넣었습니다. 사전 맨 위의 규칙은 "문제 원문이 항상 먼저다"입니다. 사전은 문제가 말하지 않은 경우를 알아차리는 데 쓰고, 없는 기능을 지어 넣는 데 쓰지 않습니다.

출처별로 신뢰도를 다르게 다뤘습니다. 실무 관례가 하나로 정해지지 않은 항목에는 `갈림` 태그를 붙였고, 문제에 답이 없으면 에이전트가 임의로 정하지 않고 결정 카드로 사람에게 올립니다. 검색 요약만 확인하고 원문을 직접 보지 못한 항목(CME 킬 스위치, Nasdaq Nordic 기준가)도 같은 태그로 구분했고, Reddit 댓글은 검증된 사실이 아니라 경험담으로 다뤘습니다.

### 외부 리뷰에서 고친 항목

T39 의 "누적 체결은 줄지 않는다"에 "체결 파기·정정 통보가 없을 때"라는 조건을 붙였습니다(GPT 의 지적). T93 의 곱셈 오버플로 처리에서 "나눗셈을 먼저"를 빼고 `__int128` 로 곱하도록 고쳤습니다. 비율을 나눗셈으로 비교하면 버림 오차가 생기기 때문입니다(Gemini 의 지적). T1 의 문장도 고쳤습니다.

## 2. 성능 사전

### 출처

| 태그 | 출처 |
|---|---|
| `[잼]` | 이 사전을 위해 직접 측정한 값 (실험 E1\~E10, 아래 절) |
| `[벤]` | 같은 PC 에서 연산 하나의 시간을 측정한 별도 벤치마크 프로젝트 |
| `[강]` | 실무자 발표·블로그: CppCon 2017 "When a Microsecond Is an Eternity", CppCon 2024 "When Nanoseconds Matter", "How to Build a Fast Limit Order Book", LMAX 아키텍처 글 등 |
| `[W]` | 웹 문서: `endl`, `from_chars`, 해시 충돌을 일으키는 키, libstdc++ 소스, 호가창 구현기 여러 편 |
| `[R]` | Reddit 스레드 113개의 요약 |
| `[L]` | LinkedIn 검색 19회에서 찾은 글 |

### 직접 측정 (E1\~E10)

- **환경**: WSL2 Ubuntu 24.04, `g++ 13.3 -std=c++20 -O2`
- **방법**: 프로그램 전체가 파일을 읽어 파일로 쓰는 시간을 20만 줄과 200만 줄 입력에서 5회씩 측정해 중앙값을 썼습니다. 0.03초 아래의 차이는 잡음으로 봅니다.
- **대상**: 입력·출력 방식, ID 조회(순차·무작위·충돌이 몰리는 키), 종목 키, 호가창 자료구조 6종 × 입력 패턴 5종, 시간 창, 집계와 상위 N, 삭제 패턴, 주문당 메모리, 코딩 습관 7가지
- **확인**: 같은 실험의 변형끼리 출력이 같은지 확인했고, ID 조회와 `endl` 은 따로 작성한 프로그램으로 한 번 더 측정해 같은 규모의 값을 얻었습니다.

### 자료가 엇갈릴 때

자료끼리 결론이 엇갈리는 주제가 있었습니다. 가격 레벨의 자료구조(실무 발표는 `vector`, 일반적인 풀이는 `map`, 개인 프로젝트는 배열), 취소 비율(95% 이상 대 30\~40%), 연결 리스트(쓰지 말라는 의견과 측정해 보니 근소하게 빨랐다는 결과)입니다. 이런 주제는 어느 한쪽을 따르지 않고 이 PC 에서 직접 측정한 값으로 정했습니다. 다른 환경의 숫자(`[R]`, `[L]`, `[강]`)는 이 PC 의 측정값과 직접 비교하지 않고, 측정하지 않은 것은 빠르다거나 느리다고 적지 않았습니다.

### 적용 등급

| 등급 | 뜻 |
|---|---|
| `[늘]` | 항상 적용 |
| `[크기]` | 최대 입력 규모에서 추정이나 측정이 기준(1초, 256MB)을 넘을 때만 적용 |
| `[말]` | 구현하지 않고 답안 주석의 "실전이라면 더 바꿀 것"에만 적음 |

필요 없는 미세 최적화를 막기 위한 구분입니다.

## 3. 사전이 실제로 쓰인 예

- **리허설 1**: GPT 리뷰가 해시 충돌 입력으로 15.2초가 걸리는 것을 재현했고, 정렬 맵으로 바꿔 0.09초가 됐습니다.
- **리허설 2**: p3 는 살아 있는 주문 100만 개에서 1초를 넘었습니다. 가격 해시와 힙을 시도했지만 효과가 없어 되돌렸습니다(원인은 캐시를 벗어나는 비용, gprof 로 확인). 20분 상한으로 재작성을 승인했고, 주문 풀·열린 주소 해시·비트 표시로 다시 작성해 최대 0.92초, 157MB 가 됐습니다.
- **리허설 3**: GPT 리뷰가 문제 1·2 에서 해시가 한 곳에 몰리는 입력을 만들었습니다. 문제 1 은 20초 넘게 걸리던 것을 0.10초로, 문제 2 는 3.8초 걸리던 것을 고쳤습니다.

모두 평범한 입력에서는 드러나지 않는 문제였습니다.
