## 1. 검사 범위와 원본 보존

하네스 정의, p1 산출물, git 이력, Codex 호출 기록, 저장된 원본 대화를 대조했다. p1은 하네스의 작동을 보여 주는 증거로 사용했다. 비공개 테스트의 정답이나 모든 입력의 정확성을 증명한 검사는 아니다.

원본을 덮어쓰지 않으려고 `qa/` 아래 임시 복사본에서 실행했다. `TMPDIR`도 그 안으로 지정했다. 기존 `VERIFY.txt`, 테스트, 구현, 결정 기록은 바꾸지 않았다. 임시 파일은 검사 뒤 제거했고, 남긴 파일은 이 보고서 하나다. 외부 모델 호출, 외부 전송, 다운로드, 설치, git 커밋·push는 하지 않았다.

`log_step.sh`는 `AI_USAGE.md`와 git을 바꾸므로 이번에는 실행하지 않았다. 사용자의 **“이외 프로젝트 수정 금지”** 지시에 따라 검사 단계와 결과를 이 보고서에 기록했다. 해당 부작용은 [log_step.sh:13](\~/cotest/scripts/log_step.sh:13), [22행](\~/cotest/scripts/log_step.sh:22)에 있다.

### 3.3 알려진 반례와 같은 오답

위 검증이 만든 두 실행 파일에 [77줄 반례](\~/cotest/problems/p1/known_fail/review2_near_boundary.in)를 각각 입력했다. 기대값은 구현 출력을 사용하지 않고, 원문의 가중 평균·손익 식을 Python `Fraction`으로 계산했다. 이 입력은 주문마다 한 번 전량 체결하므로 앞의 OK·FILL 줄도 입력에서 직접 만들었다. **77줄 전체가 기존 기대 출력 파일과 같았다.**

```text
known_fail: messages=77
Fraction expected last: POS A 2000001 1 -6
known_fail .out == independent full expected: True
main: POS A 2000001 1.000001 -5.999999; equal_expected=False
alt: POS A 2000001 1.000001 -5.999999; equal_expected=False
```

마지막 줄만 재현하는 명령은 복사본 기준으로 다음과 같다.

```bash
problems/p1/build/p1 < problems/p1/known_fail/review2_near_boundary.in | tail -1
problems/p1/build/alt < problems/p1/known_fail/review2_near_boundary.in | tail -1
```

기대값을 짧게 다시 계산하는 식도 있다. [2차 리뷰:113](\~/cotest/problems/p1/REVIEW_codex.md:113)의 식을 사용한 것이다.

```python
from fractions import Fraction as F
H = 2000001
avg = 1 + (1 - F(1, H**7)) / 2000000
pnl = -7 + sum(F(1, H**j) for j in range(7))
assert avg < F(10000005, 10**7)       # 1.0000005보다 작다
assert -pnl > F(59999995, 10**7)      # 절댓값은 5.9999995보다 크다
# 소수 6자리 반올림: 평균 1, 손익 -6
```

또한 `git show d99cfe4:problems/p1/p1.cpp`로 1차 코드를 복원하고, 보관된 1차 alt와 각각 `g++ -std=c++20 -O2`로 빌드했다. 현재 테스트 29\~31을 입력한 결과다.

| 입력 | 기대 마지막 줄 | 옛 제출 코드와 옛 alt가 함께 낸 마지막 줄 |
|---|---|---|
| 29_review_half | `POS A 640 1.573438 0` | `POS A 640 1.573437 0` |
| 30_review_pnl_exact | `POS A 0 0 1` | `POS A 0 0 1.000008` |

세 사례 모두 **두 구현의 전체 출력은 서로 같고, 기대 출력과는 달랐다.** 당시 커밋의 `VERIFY.txt`도 무작위 1000회 차이 0의 PASS다(`git show d99cfe4:problems/p1/VERIFY.txt`).

### 3.5 불변식 검사기의 범위

원본 p1 `check()` 함수에 다음 문자열을 직접 넣었다.

```text
입력: Q A\n
출력: 빈 문자열
check.py 반환: []

입력: O 1 A B 1 100\nE 1 1 1 100\nQ A\n
출력: OK 1\nFILL 1 1 0 100\nPOS A 1 100 999\n
check.py 반환: []
```

첫 사례는 조회 결과가 빠졌고, 둘째는 아직 팔지 않았는데 실현 손익 999를 출력했다. 그래도 통과한다. [check.py:64](\~/cotest/problems/p1/check.py:64)는 출력이 **더 많은 경우만** 잡고, [128행](\~/cotest/problems/p1/check.py:128)은 POS의 수량·평균 범위를 볼 뿐 손익을 검증하지 않는다. 불변식 검사기를 완전한 정답 판정기로 소개하면 안 된다.

## 5. 시간 기록의 정정과 실전 운용

| intake 시작 | 17:20:12 | C:4 |
| 카드 4개를 사용자에게 보여 줌 | 17:27:14 | C:133 |
| 첫 사람 답변 | 17:38:06 | C:136 |
| `/solve p1` 시작 | **17:56:26** | C:163 |
| “25분 초과” 중간 보고 | 18:08:47 | C:352 |
| D18·D17에 “추천대로” 답변 | **18:15:42** | C:355. 18:17:25는 결정 기록을 쓴 시각(C:360) |

JSONL 시각 차이를 계산한 출력:

```text
solve -> 25min claim: 740.694초   (12분 20.694초)
solve -> report:      2406.028초  (40분 6.028초)
D18 wait:            415.232초   (6분 55.232초)
D20 wait:            3748.795초  (62분 28.795초)
initial wait:        651.420초   (10분 51.420초)
```

따라서 **“25분에 멈췄다”와 “solve가 58분 걸렸다”는 모두 부정확하다.** 첫 사람 답변 뒤부터 solve 명령 전까지의 시간까지 포함하면 AI 작업 시간을 부풀린다. 반대로 실제 solve 40분도 25분보다 길다. D18 답 대기만 빼면 약 33분 11초이며, 이 값에는 모델·도구 대기가 포함된다. 순수 계산 시간이나 사람의 실제 고민 시간으로 단정할 수 없다.

제안은 다음과 같다.

1. intake에서 제한 시간 종료 시각과 문제 수를 받아, 제출 준비 20분을 먼저 남긴다. 제한 시간 자체는 현재 자료에 없으므로 다문제 완주 가능 여부는 미검증이다.
2. `/solve` 시작·사람 답 대기·재개·완료를 각각 기록한다. 25분의 기준이 벽시계인지 대기 제외인지 정한다. 현재는 타이머 코드가 없다.
3. 소수 출력처럼 큰 설계가 필요한 결정은 구현 전에 시간·정확성 가능성을 짧게 검토한다. D16→D18→D19의 되돌림을 줄이는 것이 우선이다.
4. 답을 기다리는 동안 다른 문제의 독립 작업을 진행하고, 예산을 넘으면 현재 소스 해시·실패 사례·다음 조치를 남겨 전환한다.
5. 독립 리뷰는 유지한다. 이번 수치 결함은 무작위 비교가 놓쳤다. 반복된 수동 보고서 편집과 같은 seed 전량 재실행의 역할부터 구별한다.

추가로 [verify.py:302](\~/cotest/scripts/verify.py:302)의 실패 입력 축소는 최대 300회 실행하며, 그 내부에는 전체 시간 예산 검사가 없다. 90초 예산은 바깥 반복 시작에서만 본다([328행](\~/cotest/scripts/verify.py:328)). 컴파일과 Python 생성기·검사기 호출에도 공통 마감 시간이 없다. **시간을 넘길 수 있는 구조는 코드 근거가 있지만, 장시간 정지 입력을 실제로 기다리는 시험은 하지 않았다.** 전체 마감 시간과 자식 프로세스 제한을 함께 두는 편이 좋다.

## 6. 결정 흐름과 사용자 관점

초기 카드는 선택지별 출력, 효과, 위험, 답변 예를 함께 보여 주었다. 사용자는 실제로 네 선택을 한 줄로 답했고, D1에서는 추천 A 대신 C를 골랐다(C:133·136). 따라서 답하는 방법은 작동했다. 이후 두 번의 “추천대로”(C:355·601)만으로 수치 정밀도와 시간 비용을 충분히 이해했다고 판단할 수는 없다.

핵심 문제는 카드 수만이 아니다.

- **D1은 출력 형식과 내부 계산 방식을 묶었다.** 정수로 출력할지와 계산 중에도 정수로 버릴지는 다른 결정이다. C 선택에 따른 큰 정수 구현·시간 비용은 “계산이 복잡해진다” 정도였다. [DECISIONS:35](\~/cotest/problems/p1/DECISIONS.md:35)와 [50행](\~/cotest/problems/p1/DECISIONS.md:50).
- **D16·D19는 문제의 빈칸이 아니라 구현 선택이다.** 특히 D19는 이미 약속한 정확성을 낮췄다. 확신도 “중간”으로 적는 것으로 사람에게 알릴 필요가 없어지지 않는다. 공통 규칙에는 “여러 줄이 한꺼번에 틀림”이라는 별도 기준도 있다. [AGENTS:23](\~/cotest/AGENTS.md:23), [DECISIONS:19](\~/cotest/problems/p1/DECISIONS.md:19).
- **카드 7개는 현행 5개 상한 위반이지만, 중요한 위험을 숨겨 5개로 맞추면 더 나쁘다.** 처음 묻는 항목과 나중에 발견한 결함을 구분하고, 추가 질문이 생긴 원인을 기록해야 한다. [intake:32](\~/cotest/.claude/skills/intake/SKILL.md:32)의 “넘으면 잘라 나머지는 AI가 정함”도 필수 보고 기준과 충돌할 수 있다.
- **D20의 선택지는 현재 구현 방식에 치우쳤다.** 상한을 조금·많이·전혀 두지 않는 세 방법이다. 출력 요구를 문제를 낸 쪽에 물을 수 있는지, 다른 문제로 이동할지, 다른 알고리즘을 검토할지 같은 선택도 보여 줄 수 있다. 특정 구현의 55초 측정으로 모든 정확한 방법이 느리다고 결론 내릴 수는 없다. [DECISIONS:174](\~/cotest/problems/p1/DECISIONS.md:174).
- **“일부러 만든 입력만 틀림”, “평가에 나올 가능성이 아주 낮음”은 확률 근거가 없다.** 테스트는 일부러 경계를 겨냥할 수 있다. “77줄 정상 입력에서 오답이 재현됨, 비공개 테스트 빈도는 모름”으로 설명하는 편이 정확하다. [DECISIONS:176](\~/cotest/problems/p1/DECISIONS.md:176), [186행](\~/cotest/problems/p1/DECISIONS.md:186).

카드에는 구현 용어보다 **어떤 답이 틀릴 수 있는지, 추가 시간이 어느 정도인지, 사용자가 지금 결정할 것이 무엇인지**를 앞에 두는 것이 좋다. 큰 정수·분모·10^-45는 보충 설명으로 두고, 근거 없는 난이도·확률 단정은 피한다. 작은 정답 사례는 링크만 보내지 말고 메시지에 입력·출력을 함께 보여 주는 기존 solve 규칙을 지킨다.

설명서도 정합성 점검이 필요하다. [EXPLAIN:9](\~/cotest/problems/p1/EXPLAIN.md:9)는 “정확히 계산하고 출력할 때만” 바꾼다고 쓰지만 [63행](\~/cotest/problems/p1/EXPLAIN.md:63)은 내부 근사를 설명한다. [173행](\~/cotest/problems/p1/EXPLAIN.md:173)은 AI 결정 전부를 “두 모델이 같은 선택”이라고 묶지만, [DECISIONS:18](\~/cotest/problems/p1/DECISIONS.md:18)의 D15·D19에는 그런 합의가 없다. 사람이 처음 읽는 요약에도 알려진 한계를 일관되게 표시해야 한다.

## 9. 다음 QA의 합격 조건과 이번 미검증 범위

수정 후에는 다음을 하네스 자체 시험에 넣는 것이 좋다.

1. 알려진 정상 범위 오답이 있으면 일반 PASS가 나오지 않는다. 부분 점수 제출을 선택해도 실패 수가 남는다.
2. 최종 관문에서 무작위 0회, 필수 파일 누락, 오래된 검증 결과를 구분해 거절하거나 명시적인 미검증 상태로 처리한다.
3. 같은 오답을 내는 두 구현을 작은 정확한 계산기가 잡는다. 반올림 경계, 큰 손익 뒤 작은 이익, 긴 감소·증가 반복을 포함한다.
4. Codex 비정상 종료·시간 초과·불완전한 파일이 성공으로 바뀌지 않는다.
5. 문맥 요약·6시간 초과·여러 작업 동시 진행 뒤에도 해당 작업의 필수 대화가 빠짐없이 묶이고, 다른 작업이 섞이지 않는다.
6. 기계 시각으로 전체 제한 시간 예산을 지키고, 보고서 수치·해시가 마지막 제출 파일과 연결된다.

실제 다문제 과제, 비공개 평가 형식, 실제 Codex 장애 뒤 Agent 전환, 장시간 정지 입력에 대한 시간 상한, 모든 수치 입력의 정확성은 **미검증**이다. 제안한 수정도 아직 적용·검증하지 않았다.
