# 하네스 품질 검사: 교차 검토 (Claude)

- 검사일: 2026-11-12. 대상 커밋: `2153a08`. 검사자: Claude Code (Fable 5.2, 데스크톱 앱).
- 기준: `qa/HARNESS_QA_BRIEF.md`. 교차 대상: `qa/HARNESS_QA_REPORT.md` (Codex).
- 이 검사 단계에서는 기존 파일을 고치지 않았다. 측정은 `/tmp` 복사본에서 했다.
- 한계: 하네스를 만든 쪽도 이 검토자도 Claude다. 그래서 Codex 보고서를 기준으로 삼고, 이 문서는 "동의 여부"와 "Codex가 보지 않은 것"만 적는다.

## 1. 결론

**구조는 유지한다. 판정 규칙과 사람의 자리를 고친다.**

검증의 뼈대(정답 사례, 독립 구현 비교, 컴파일러 검사, 다른 모델의 리뷰)는 첫 연습에서 실제로 결함을 잡았다. 문제는 세 가지다.

1. **PASS 가 실제보다 강하게 읽힌다.** 알려진 오답, 생략된 검사, 실행되지 않은 코드가 있어도 PASS 다.
2. **사람이 들어갈 자리가 "카드에 답하기"뿐이었다.** 그 카드도 비용을 알려 주지 않았다. 사람이 고른 D1-C 하나가 약 30분과 추가 결정 3개로 이어졌는데, 카드에는 "계산이 복잡해진다" 한 줄뿐이었다.
3. **작업자가 멈출 줄 모른다.** 문제에 없는 정밀도 요구를 스스로 만들고 거기에 solve 시간의 대부분을 썼다. 실전(150분, 여러 문제)이었다면 다른 문제를 풀 시간이 없었다.

## 2. Codex 보고서와의 대조

| Codex의 지적 | 판정 | 내가 확인한 근거 |
|---|---|---|
| 알려진 오답이 있어도 PASS, 제출 복사 | 동의 | `verify.py` 는 `tests/*.in` 만 모은다. `known_fail/` 을 읽는 코드가 없다 |
| 두 구현이 같은 오답 (H1) | 동의. 원인 진단도 동의 | alt 에게 `DECISIONS.md` 전체를 준다(`codex_ask.sh` alt 모드). D16, D19 같은 "구현 방법"이 그대로 전달된다 |
| 검사를 생략하거나 무작위 0회여도 최종 관문 통과 | 동의 | `--final` 은 FAIL 만 본다. SKIP 과 실행 횟수는 판정에 쓰이지 않는다 |
| Codex 가 오류로 끝나도 파일만 있으면 성공 | 동의 | `codex_ask.sh` 는 종료 코드를 `rc` 에 담고도 파일 존재만 본다 |

| 고정 seed 는 결함이 아님 (H6) | 동의 | 재현에는 고정이 필요하다. 새 seed 묶음을 더하면 된다 |
| 불변식 검사기는 정답 판정기가 아님 | 동의 | p1 `check.py` 는 POS 의 손익을 검증하지 않는다 |

**Codex와 다르게 보는 점**

- Codex 는 알려진 실패가 있으면 "정확성 판정은 FAIL 유지"를 제안한다. 방향은 같지만, 판정을 셋으로 나누는 편이 사람에게 더 쓸모 있다: `PASS` / `조건부 (사람의 승인 필요: 사유 목록)` / `FAIL`. 실전에서는 "알려진 한계를 안고 제출"이 합리적인 선택일 수 있고, 그 선택은 사람의 몫이다. 승인 없이는 `submit/` 에 복사하지 않는다.
- Codex 는 독립 구현의 수정(H13)에 "독립 작성자에게 다시 맡기기"를 제안한다. 한 번 호출에 3\~4분이 든다. 실전에서는 작업자가 고치되 **원문의 어느 문장 때문인지와 고친 사람을 `ALT_NOTES.md` 에 남기는 것**으로 충분하다고 본다. 대신 원인(결정이 `EDGE.md` 에만 있고 `DECISIONS.md` 에 없었던 것)을 막는다.

## 3. Codex가 보지 않은 것

과제의 목적(예외 처리를 제대로 다루는가, AI로 검증까지 해내는가)을 기준으로 다섯 가지를 더 보았다.

### 3.1 "예외 가지를 시험했다"는 주장을 기계가 재지 않는다

하네스는 예외 표(`EDGE.md`)와 테스트 파일의 대응을 글자로만 적는다. 코드의 예외 처리 줄이 시험에서 실제로 실행됐는지는 아무도 재지 않는다. 그래서 직접 쟀다.

```text
명령: g++ -std=c++20 -O0 --coverage p1.cpp → tests/*.in 실행 → gcov -b
1층 정답 사례(작은 29개)만:        실행된 줄 91.47% (375줄 중), 실행 안 된 줄 27
1층 전부(큰 2개 포함):             실행 안 된 줄 21
1층 + 무작위 200개:                실행된 줄 93.87%, 실행 안 된 줄 18
```

끝까지 실행되지 않은 18줄 가운데 **11줄이 `p1.cpp` 220\~230행, 곧 D19의 "분모가 크면 반올림" 코드다.** 알려진 오답을 만드는 바로 그 코드가 정답 사례 31개와 무작위 입력 어디에서도 한 번도 실행되지 않았다. 검증 표는 PASS 였다.

좋은 소식도 있다. 입력 검증과 거부 가지(잘못된 숫자, 한도, 없는 주문 등)는 모두 실행됐다. p1 의 예외 처리 시험은 충실했다. 다만 그 사실을 보여 주는 근거가 지금까지는 없었다.

**고칠 것**: 검증 표에 "실행되지 않은 줄" 행을 넣는다. 한 번도 실행되지 않은 줄은 검증되지 않은 줄이다.

### 3.2 테스트가 버그를 잡을 힘이 있는지 문제마다 재지 않는다

하네스 자체 시험은 예제 문제 s1 에 버그 8개를 넣어 본다. 실제 문제의 테스트가 그만한 힘이 있는지는 모른다. 통과한 테스트 31개가 `<` 와 `<=` 의 차이를 구별하는지 확인할 방법이 없다.

**고칠 것**: 제출 코드에 작은 변형(비교 연산자, 조건 결합)을 자동으로 넣어 테스트가 잡는지 센다. 살아남은 변형은 "시험되지 않은 경계"다.

### 3.3 "사람이 확인한 정답 사례"가 이름뿐이다

설계상 1층은 사람이 확인한 정답 사례다. 실제로는 31개 모두 AI가 손으로 구했고, 사람의 확인은 보고서의 빈 체크 칸으로 남았다. 완료 메시지는 사례를 보여 주지 않고 파일 경로만 알려 주었다. 두 모델이 문제를 같은 방식으로 잘못 읽으면 이 하네스는 잡지 못하는데, 그것을 깰 수 있는 유일한 자리가 비어 있었다.

**고칠 것**: 작은 사례 3개를 메시지에 그대로 보여 주고 사람의 확인을 받는다. 확인한 사례를 파일로 표시하고 검증 표에 개수를 싣는다.

### 3.4 진행 상황을 볼 곳이 없다

사용자가 "과정이 눈에 보이지 않았다"고 했다. 지금 상태를 알려면 대화를 거슬러 읽거나 파일 여섯 개를 열어야 한다. 문제별 단계, 경과 시간, 마지막 판정, 답을 기다리는 카드를 한 화면에 모은 것이 없다.

**고칠 것**: 파일에서 상태를 읽어 표 하나로 보여 주는 현황판. 사람이 다른 터미널에 띄워 둔다.

### 3.5 비용에 대한 규칙이 없다

- 카드 형식에 "이 선택지를 고르면 몇 분이 더 드는가"가 없다. "나중에 바꾸는 비용"은 코드 규모만 적는다.
- "문제에 없는 요구를 스스로 만들지 않는다"는 규칙이 없다. p1 은 원문에 없는 임의 정밀도를 정답 조건으로 삼았다.
- 한 가지 세부에 쓸 시간의 상한이 없다.
- 과제 전체의 시간 배분(문제 수, 종료 시각, 제출 준비 20분)이 intake 에 없다.
- 문제를 차례로 풀면 문제당 40분 × 3문제 = 120분에 접수 15분, 제출 20분을 더해 150분을 넘는다. 문제를 나누어 동시에 푸는 방법이 정해져 있지 않다.

## 5. 이 검토에서 하지 않은 것

- 원본 대화(jsonl)의 시각을 다시 계산하지 않았다. Codex 의 시간 정정을 그대로 받아들였다.
- Codex 의 실패 경로 시험(가짜 Codex, 무작위 0회)을 다시 돌리지 않았다. 코드를 읽어 같은 결론임을 확인했다.
- 여러 문제를 동시에 푸는 실전 흐름은 아직 아무도 돌려 보지 않았다.
