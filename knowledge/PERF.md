# 속도·메모리 사전 (OMS)

그럴듯해 보이는 답안이 어떤 입력에서 느려지거나 메모리를 많이 쓰는지, 그리고 무엇으로 바꾸면 되는지를 모았다.
`TRAPS.md` 가 "무엇을 출력해야 맞는가"를 다룬다면, 이 사전은 "맞는 출력을 제때, 적은 메모리로 내는가"를 다룬다.

**순서는 늘 같다.** 맞게 동작한다 → 복잡도의 급이 맞다(메시지마다 전체를 훑지 않는다) → 싸고 안전한 습관 → 그다음은 재 보고 필요할 때만.
이 사전의 숫자 대부분은 셋째 단계까지가 평가 점수의 거의 전부라는 것을 보여 준다.

**쓰는 법**
- 접수(`/intake`): "0. 크기로 고르기"에서 자료구조를 고르고, `DECISIONS.md` 의 "효율 계획" 표 근거 칸에 `S번호`를 적는다. "가장 느려지는 입력" 칸은 Z절에서 고른다.
- 풀이(`/solve`): 큰 입력이 느리거나 메모리가 크면 해당 절을 본다. 답안 맨 위 주석의 "실전이라면 더 바꿀 것"은 J절에서 고른다.
- 리뷰(`codex_ask.sh review`): 리뷰어가 이 사전을 받아 해당 항목을 판정하고, Z절의 모양으로 큰 입력을 만들어 잰다.
- 독립 구현(`codex_ask.sh alt`): Z절만 받는다. 두 번째 생성기의 `gen_big` 에 쓴다.

**등급**
- `[늘]` 언제나 지킨다. 싸고 틀릴 일이 없다. 대부분 `templates/main.cpp` 에 이미 들어 있다.
- `[크기]` 문제의 최대 크기에서 어림이나 측정이 기준(1초, 256MB)을 넘을 때만 쓴다.
- `[말]` 구현하지 않는다. 문제 크기에서는 차이가 없거나, 틀릴 위험이 더 크다. 답안 주석의 "실전이라면 더 바꿀 것"에만 쓴다.

**근거 표기**
- `[잼]` 이 PC 에서 이 사전을 위해 잰 값(2026-11-13). Ryzen 5 7500F, WSL2 Ubuntu 24.04, `g++ 13.3 -std=c++20 -O2`. **프로그램 전체**가 파일을 읽어 파일로 쓰는 데 걸린 시간, 5번 가운데 값. 20만 줄 / 200만 줄 순서로 적는다. 0.03초 아래의 차이는 잡음이다. 측정 프로그램은 이 저장소에 넣지 않았다.
- `[벤]` 별도의 벤치 프로젝트(아직 공개 전)에서 잰 연산 하나의 시간(나노초).
- `[R]` Reddit 스레드를 다른 에이전트가 요약한 것. `[L]` LinkedIn 글(대부분 학생·취미 프로젝트의 자기 측정). `[W]` 웹 문서. `[강]` 실무자 발표·블로그. 숫자는 그 글의 환경에서 나온 것이라 이 PC 의 숫자와 견줄 수 없다.
- 표기가 없는 문장은 일반 원리다. 재지 않은 것은 빠르다거나 느리다고 적지 않았다.

## 0. 크기로 고르기 (먼저 본다)

기준: 큰 입력이 1초 안, 메모리 256MB 안(`verify.sh` 가 잰다). 어림할 때는 **줄당 1마이크로초면 100만 줄에 1초**로 계산한다.
가장 단순한 것이 기준 안에 들어오면 그것을 쓴다. 아래 숫자는 모두 `[잼]`.

| 고를 것 | 20만\~30만 줄까지 | 100만 줄 이상 | 잰 값 |
|---|---|---|---|
| 정수 번호 → 주문 | `std::map`. 가장 단순하고 어떤 번호에도 안전하다 | `unordered_map` + 섞는 해시 + `reserve`(S11). 번호가 1..N 으로 빽빽하다고 **원문에 적혀 있으면** `vector` 색인(S13) | 넣기·찾기·지우기 50만 번: map 0.11\~0.13초. 250만 번: map 1.3\~1.7초, 섞는 해시 0.6\~0.7초. 500만 번: map 3.2\~4.5초, 섞는 해시 1.7\~1.8초, vector 0.12초 |
| 종목 글자 → 상태 | `std::map<string, …>` | `unordered_map<string, …>`. 메시지마다 한 번만 찾아 참조를 들고 쓴다(S15) | 메시지당 4번 조회: 20만 줄은 무엇이든 0.07초 안. 200만 줄: map 0.64초, unordered_map 0.19초 |
| 호가창 | 가격 `map` + 단계마다 `list` + 번호→위치(S20) | 같다 | 다섯 가지 최악 모양 모두 0.02\~0.06초 / 0.20\~0.95초 |
| 시간 창의 합·최대 | 창 안에 수십 건이면 다시 훑어도 된다. 수천 건 이상이면 S33, S34 | S33, S34 | 창 안에 5만 건: 다시 훑기 3.85초 / 42초, 단조 덱 0.02초 / 0.23초 |
| 상위 N 조회 | 조회가 드물면 `partial_sort`, 잦으면 `set` 유지(S40) | `set` 유지 | 종목 5,000개, 조회 30%: 전체 정렬 11.4초, partial_sort 0.30초, set 0.04초 (20만 줄) |
| 읽기와 쓰기 | `getline` + `from_chars`, `cout << … << '\n'` (템플릿 그대로) | 같다 | 200만 줄 읽기 0.115초, 쓰기 0.21초 |

**최대 크기가 원문에 없으면** 100만 줄로 어림하고 `map` 으로 시작한다. `gen_big` 을 100만 줄로 만들어 재고, 0.5초를 넘으면 그때 S11 로 바꾼다.

| S18 | `unordered_map` 을 돌며 출력한다 | - | 순서가 정해져 있지 않아 출력이 틀린다. 섞는 해시를 쓰면 실행마다 달라진다 | 출력 순서가 필요하면 `map`, 또는 끝에 한 번 정렬 | [늘] |

**섞는 해시** (S11. 100만 줄 이상이고 번호가 빽빽하지 않을 때만 넣는다)

```cpp
struct MixHash {   // 번호를 고르게 흩는다(splitmix64). 버킷 수의 배수로 맞춘 번호에도 몰리지 않는다
    std::size_t operator()(long long x) const noexcept {
        static const std::uint64_t seed =
            static_cast<std::uint64_t>(std::chrono::steady_clock::now().time_since_epoch().count());
        std::uint64_t z = static_cast<std::uint64_t>(x) + seed + 0x9e3779b97f4a7c15ULL;
        z = (z ^ (z >> 30)) * 0xbf58476d1ce4e5b9ULL;
        z = (z ^ (z >> 27)) * 0x94d049bb133111ebULL;
        return static_cast<std::size_t>(z ^ (z >> 31));
    }
};
std::unordered_map<long long, Order, MixHash> orders;   // <chrono>, <cstdint> 필요. 이 맵을 돌며 출력하지 않는다(S18)
```

## C. 호가창

| 번호 | 느린 모양 | 드러나는 입력 | 왜 느린가, 얼마나 | 바꿀 모양 | 등급·근거 |
|---|---|---|---|---|---|
| **S20** | (기본 구조) | Z1\~Z4 모두 | 매수·매도 각각 `map<가격, 단계{수량 합계, list<주문>}>`, 그리고 번호 → {방향, 가격, `list` 반복자}. 넣기 O(log 단계 수), 취소 O(1) + 번호 찾기, 체결 O(체결 건수). 다섯 모양 모두 0.02\~0.06초 / 0.20\~0.95초, 메모리 최대 36MB / 332MB | 이것을 쓴다. 빈 단계는 `map` 에서 지운다 | [늘][잼]. 일반적인 풀이으로 가격 → 대기열 맵이 적당하다 [R] |
| **S21** | 취소할 때 대기열(`deque`, `vector`)에서 번호를 훑어 찾는다 | 한 가격에 몰리고 뒤에서부터 취소 (Z1) | 취소마다 대기열 길이만큼. **3.5초 / 60초 초과**. 평범한 입력에서는 기본 구조와 같아서(0.02초) 드러나지 않는다 | 번호 → 대기열 속 위치(S20). 실제 시장도 메시지의 다수가 취소다(T122) | [늘][잼]. 취소 4.6ms 대 260ns [L] |
| S22 | 조회 때 그 가격의 수량을 대기열을 돌며 더한다 | 매 줄 뒤에 조회 (Z2) | 조회마다 대기열 길이만큼(T165). 훑는 취소와 함께 잰 값: 0.43초 / 40초 (기본 구조 0.03초 / 0.42초) | 단계에 합계를 두고 넣기·취소·체결 때 고친다 | [늘][잼] |

## J. "실전이라면 더 바꿀 것"에 쓸 문장

답안이 **실제로 쓴 구조**에 해당하는 것만 두세 줄 고른다. 숫자를 붙이려면 이 사전의 `[잼]` 값과 조건을 같이 적는다.

| 답안이 쓴 것 | 주석에 쓸 말 |
|---|---|
| 번호 → 주문을 `map` / `unordered_map` | 노드마다 따로 할당돼 조회 한 번이 캐시를 한두 번 벗어난다. 실전이라면 미리 잡아 둔 배열이나 열린 주소 해시로 바꾸고, 장중에는 할당하지 않는다 |
| 가격 단계를 `map` | 가격 범위가 정해진 종목이면 틱 번호 배열로 바꾼다. 이 PC 에서 200만 줄 최악 모양에 0.95초 → 0.36초였고 평범한 입력에서는 차이가 없어 쓰지 않았다 |
| 단계의 대기열을 `list` | 주문을 풀에 두고 앞뒤 색인으로 이으면 주문마다의 할당이 없어진다 |
| 글자 입력을 줄마다 읽기 | 실전의 입력은 글자가 아니라 길이가 정해진 이진 전문이라 나누고 변환하는 일이 없다 |
| 종목을 `string` 키로 | 접수 때 한 번 번호로 바꿔 배열로 조회한다 |
| 총 시간으로 잼 | 실전에서는 평균이 아니라 꼬리(p99, p99.9)와 첫 메시지의 지연을 본다. 이 과제에서는 재지 않았다 |
| 한 스레드 | 실전에서도 매칭과 주문 상태는 한 스레드가 순서대로 처리하고, 입출력만 큐로 나눈다 [강] |

## Z. 큰 입력 모양

`gen_big` 과 리뷰에서 쓴다. 문제의 최대 크기(원문에 없으면 100만 줄)로 만든다. **평범한 큰 입력 하나에, 이 문제의 메시지 종류에 해당하는 모양을 둘 이상 더한다.**
입력은 문제의 형식에 맞는 정상 메시지로 만든다(Z9 만 예외). 깨진 줄로 채우면 느린 길을 지나가지 않는다.

| 번호 | 모양 | 무엇을 드러내나 |
|---|---|---|
| Z1 | 한 가격(또는 한 종목·한 키)에 주문을 절반 넣고, 가장 나중 것부터 거꾸로 취소 | 대기열을 훑는 취소·정정(S21) |
| Z2 | 주문을 조금 넣은 뒤 줄마다 조회 | 조회 때 다시 더하기(S22, S39) |
| Z3 | 주문마다 새 가격, 최우선에서 점점 멀어지게. 사이사이 조회 | 정렬 `vector` 끼워 넣기(S24), 단계마다의 메모리(S23) |
| Z4 | 수만 단계를 쌓은 뒤 큰 주문 몇 개가 전부 휩쓴다 | 매칭 반복문, 단계 지우기(S24) |
| Z5 | 시각이 거의 같은 메시지 수만 건(창 하나에 다 들어온다) | 창 다시 훑기(S33, S34) |
| Z6 | 모든 체결이 한 종목에, 체결마다 그 종목 조회 | 다시 더하기(S39) |
| Z7 | 주문 절반 + 전체 취소·긴급 정지 명령 절반 | 명령마다 전부 훑기(S41) |
| Z8 | 해시가 몰리는 번호: 번호 = k × P. P 는 번호 개수 N 이상인 첫 값: 20753, 42043, 85229, 172933, 351061, 712697, 1447153, 2938679. 답안이 `reserve(n)` 을 쓰면 `unordered_map<long long,int> m; m.reserve(n); m.bucket_count()` 로 P 를 구한다 | 정수 키 `unordered_map`(S11). 정수 키 `unordered_map` 을 쓰는 답안에만 넣는다 |
| Z9 | 전부 깨진 줄(글자 섞인 숫자, 필드 부족) | 예외로 처리하는 답안(S8), 오류 출력 경로 |
| Z10 | 상위 N·순위 조회가 줄의 30% | 조회마다 정렬(S40) |
| Z11 | 한 대기열에 깊게 쌓고 앞에서부터 하나씩 소비 | 앞에서 지우기(S46) |
| Z12 | 조각으로 오는 전문: 수만 개가 한 버퍼에 이어 붙는다 | 버퍼 앞 자르기(S46, T175) |
| Z13 | 한 조건에 수만 건이 한꺼번에 해당(한 번에 대량 삭제·만료) | 하나씩 지우기(S47) |
| Z14 | 번호와 종목이 모두 다르고 아무것도 끝나지 않는다 | 최대 메모리(S45, S49) |
