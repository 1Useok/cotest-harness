# 문서 형식

모든 문서는 쉬운 한국어로 짧게 쓴다.

## SPEC.md (정리한 요구사항)

```
# pN 요구사항
## 한 줄 요약
## 입력 형식        (메시지 종류별 필드, 구분 문자, 숫자의 범위)
## 출력 형식        (메시지 종류별 출력, 공백과 줄바꿈)
## 규칙            (번호를 붙인다. 각 규칙 끝에 원문의 위치를 적는다)
## 예제            (원문의 예제를 그대로)
## 크기와 시간      (원문에 적힌 최대 크기: 메시지 수, 주문 수, 값의 범위. 시간·메모리 제한이 있으면 그대로.
##                  없으면 "원문에 없음"이라 적고, 최대 크기에서 1초 안에 끝나는 것을 목표로 삼는다)
## 원문에 없는 것   (번호를 붙인다. DECISIONS.md 의 항목 번호와 맞춘다)
```

원문에 없는 내용을 SPEC에 지어 넣지 않는다. 없는 것은 "원문에 없는 것"에 적는다.

## EDGE.md (예외 표)

| # | 상황 | 입력 예 | 기대 출력 | 근거 | 테스트 파일 |
|---|---|---|---|---|---|
| E1 | 수량이 소수 | `N 1 A B 100 10.5` | `BAD` | 문제 3절 | 02_bad.in |
| E2 | 정확히 한도 | ... | ... | D2 (AI가 정함) | 03_limit.in |

근거는 셋 중 하나다: `문제 N절`, `D번호 (AI가 정함)`, `D번호 (사람이 정함)`. 실무 함정 사전에서 온 행은 `T번호`를 함께 적는다(예: `문제 4절, T40`).

- 행 번호는 `E1`, `E2` … 로 쓴다. 표의 칸 수(6칸)를 지킨다. `verify.sh` 가 이 표를 읽어, 테스트 파일이 없는 행과 기대 출력이 빈 행을 알려 준다.
- "테스트 파일" 칸에는 `tests/` 안의 실제 파일 이름을 적는다. 무작위 검사로만 보는 행은 `check.py`, 고치지 못한 반례는 `known_fail/파일이름` 이라고 적는다.
- 입력 예나 기대 출력에 `|` 글자가 들어가면 `/` 로 바꿔 적는다.

## DECISIONS.md (결정 기록)

```
# pN 결정 기록

## AI가 정한 것
| # | 질문 | 선택 | 근거 | 확신도 | Codex의 선택 |
|---|---|---|---|---|---|
| D0 | 입력 나누기와 숫자 표기 | (나누기) 줄 끝 `\r` 과 줄 앞뒤의 공백·탭은 지운다. 필드 사이에 공백·탭이 여러 개여도 구분 하나로 본다. 그렇게 나눈 필드 수가 맞지 않으면 형식이 깨진 줄이다. (숫자) 칸 전체가 10진 정수일 때만 숫자다. 앞의 0 은 받는다(`007` 은 7). `-` 는 맨 앞 하나만 받는다(`-3` 은 음수 3, `-0` 은 0). `+5`, `1.5`, `1e3`, 빈 칸, 64비트를 넘는 수는 숫자가 아니다. 값이 범위 안인지는 그다음에 본다 | 원문의 "공백 하나로 나뉜다"는 정상 입력의 모양을 말한 것으로 읽는다. 평가용 기준 풀이는 대개 공백 단위로 읽는다(`cin >>`, `split()`). 글자 그대로 자르면 줄 끝 공백 하나에 그 줄 전체를 잃는다. 숫자 표기는 뼈대 코드의 `parse_int`(`std::from_chars`)와 같게 맞춘 것이다. 문제마다 달리 정하면 답안, 독립 구현, 교차 확인이 `+1` 이나 `-0` 에서 갈린다 | 중간 | (접수 때 채운다) |
| D1 | 빈 줄을 어떻게 하나 | 건너뛴다 | 예제에 빈 줄 출력이 없다 | 높음 | 같음 |

(D0 은 모든 문제의 첫 행이다. 기본값은 위와 같고, 아래 경우에만 고쳐 적는다.
 - 공백이 자료인 문제(고정 폭 전문, 바이트 흐름): "줄 끝 `\r` 만 지운다. 공백은 다듬지 않는다".
 - 구분 문자가 쉼표 같은 다른 글자: "그 글자로만 나눈다. 빈 필드를 살린다. 필드 앞뒤 공백만 뗀다".
 - 원문이 공백의 개수나 탭을 오류 조건으로 적었다: 원문을 따른다.)

## 사람에게 올린 것
(아래 결정 카드. 답을 받으면 "- 결정: A (사람, 15:32)" 줄을 덧붙인다. 현황판이 이 줄로 답을 받았는지 센다)

## 구현 메모
(자료형, 알고리즘, 성능을 위한 선택. 출력 규칙이 아닌 것만. 독립 구현에게는 이 절을 보여 주지 않는다.
 여기 적은 선택 때문에 출력이 달라질 수 있으면 메모가 아니라 결정 카드다)

### 효율 계획 (코드를 쓰기 전에 채운다)
| 연산 | 자료구조 | 시간(메시지 하나당) | 가장 느려지는 입력 (PERF 의 Z절) | 근거 (PERF 의 S번호) |
|---|---|---|---|---|
| 주문 넣기 | map<가격, list<주문>> + 번호→위치 map | O(log 가격 단계 수) | Z3 가격이 모두 다름 | S20 |
| 취소 | 번호→위치로 바로 지움 | O(log 주문 수) | Z1 한 가격에 주문 20만 개, 뒤에서부터 취소 | S21 |
- 최대 크기(SPEC 의 "크기와 시간")에서 전체 연산 수 어림: 예) 20만 × log(20만) ≈ 350만
- 메모리 어림: 예) 주문 하나 약 100바이트 × 20만 = 20MB
- 더 단순한 방법과 그것을 고르지 않은 이유 한 줄: 예) 매번 대기열을 훑으면 취소가 O(n), 최악 20만 × 20만
- 더 빠른 방법과 그것을 쓰지 않는 이유 한 줄(실전이라면 바꿀 것): 예) 가격 단계를 틱 번호 배열로. 이 크기에서는 차이가 없고 가격 범위의 경계 처리가 늘어난다
```

"AI가 정한 것"과 "사람에게 올린 것"에는 **무엇을 출력하는가**만 적는다. "long double 을 쓴다" 같은 구현 방법을 적으면 독립 구현이 같은 방법을 따라 해서 같은 곳에서 함께 틀린다.

### 결정 카드

```
### D3. 취소된 주문에 체결이 도착하면?
- 원문: 4번 "취소된 주문은 더 이상 변하지 않는다". 체결이 오는 경우는 적혀 있지 않다.
- 예시 입력: `N 7 A B 100 10` / `C 7` / `F 7 3`

| | A. 거부한다 (추천) | B. 체결을 반영한다 |
|---|---|---|
| 마지막 줄의 출력 | `REJECT 7 NOT_ACTIVE` | `FILL 7 3 7` |
| 근거 | 원문 문장 그대로 | 실제 거래소에서는 취소 확인 전에 체결이 올 수 있다 |
| 틀렸다면 | 이 경우의 줄만 틀린다 | 이 경우의 줄만 틀린다 |
| 추가 시간 | 0분 | 약 5분 |

- 추천: A (확신도 중간). Codex 는 B.
- 나중에 바꾸는 비용: 함수 하나, 약 5분
```

카드를 쓰는 규칙
- **카드는 한 화면에 들어와야 한다.** 위 형식에서 줄을 늘리지 않는다. 사람이 30초 안에 고를 수 있어야 한다.
- OMS를 잘 모르는 사람이 읽고 고를 수 있어야 한다. 용어를 쓰면 한 줄로 풀이한다. 한국어로 쓴다.
- 선택지 가운데 하나는 반드시 **원문의 글자를 그대로 따르는 것**이다(원문에 조건이 없으면 조건 없이 처리하는 선택지). 그 선택지에 "원문 글자 그대로"라고 적는다. 원문이 그 경우를 아예 말하지 않으면 "원문에 없음: 아무것도 더하지 않는다"라고 적는다.
- "추가 시간"은 구현, 테스트, 재검증을 합친 어림값이다. 10분을 넘는 선택지는 "다른 문제 하나를 풀 시간"이라고 적는다. 어림할 수 없으면 "모름(구조를 바꿔야 함)".
- 한 카드에는 한 가지만 묻는다. 서로 다른 명령(예: C, CA, CR)의 처리를 한 카드에 묶지 않는다. "어떻게 출력하나"와 "속으로 어떻게 계산하나"도 묶지 않는다.
- 근거 없는 확률("평가에 나올 가능성이 아주 낮다")을 적지 않는다. 아는 사실만 적는다.
- "원문" 줄에는 갈리는 문장을 **그대로 인용**한다(한 문장). 인용할 문장이 없으면 "원문에 없음"이라고 적는다. 출력 칸에는 예시 입력의 마지막 줄에 실제로 찍힐 줄을 글자 그대로 적는다(지어낸 이유 글자면 뒤에 `(지어낸 글자)`).
- **추천은 `AGENTS.md` 의 "추천을 고르는 기준"으로 고른다.** 값이 없으면 막는 쪽, 통보는 버리지 않는 쪽, 조용히 넘기지 않는 쪽이 추천이다. "원문 글자 그대로"가 추천이 아닐 수 있다. 근거 칸에 어느 기준인지 한마디로 적는다. "출력 없이 버린다"는 선택지에는 무엇을 잃는지(예: 포지션이 실제와 달라진다)를 적는다.
- 거부 줄이나 오류 줄을 **낼지 말지**는 근거가 있는 결정이다(기준 3번). 사람이 답할 근거가 없는 것은 그 줄의 **글자**뿐이다.
- **사람이 답할 근거가 없는 것은 카드로 올리지 않는다.** 원문에 없는 오류 줄의 글자(`ERR INVALID` 로 할지 `ERR BAD` 로 할지)처럼 원문으로도 실무 지식으로도 고를 수 없는 것은 AI가 정하고, "AI가 정한 것" 표의 근거 칸에 "지어낸 글자"라고 적고, 보고서의 "이 검증이 놓칠 수 있는 것"에 적는다.
- 사람에게 처음 올리는 카드는 문제당 3장까지다. 넘으면 틀렸을 때 영향이 큰 순서로 3장만 올리고, 나머지는 AI가 정해 표에 "확신 낮음"으로 표시한다. 사람은 표를 보고 뒤집을 수 있다.

문제를 낸 쪽에 질문할 수 있는 과제일 때 (과제 안내문에 그렇게 적혀 있을 때만)
- 카드 가운데 틀리면 여러 줄이 틀리는 것만 골라, 메일에 그대로 붙일 수 있는 질문을 `logs/QUESTIONS.md` 에 한 묶음으로 쓴다. 질문 하나는 한 문장이고 예시 입력 한 줄을 붙인다.
- 보낼지는 사람이 정하고 사람이 보낸다. 답을 기다리는 동안 추천안으로 진행한다.
- 안내문에 질문에 관한 말이 없으면 이 파일을 만들지 않는다.

## REPORT.md (문제별 보고)

```
# pN 보고

## 판정
(PASS / 조건부 / FAIL. VERIFY.txt 의 판정 그대로 한 줄. 조건부면 이유를 그대로 옮긴다)

## 사람이 한 일
(이 문제에서 사람이 정한 것. 사람의 말을 그대로 옮긴다. 하지 않은 일을 적지 않는다)
- 결정: D1 C (추천은 A였다), D3 A …
- 탐침: "보유보다 많이 팔면?" → 출력 확인, 테스트 32 로 추가
- 받아들인 한계: (있으면. 사람이 말한 사유)

## 정답 사례 교차 확인
(VERIFY 표의 "정답 사례 교차 확인" 값을 그대로: 몇 개 중 몇 개가 다른 모델이 원문만 보고 구한 출력과 같았나.
 달랐던 사례마다 한 줄: 어느 쪽이 맞았고 무엇을 고쳤나. xcheck/RESOLVED.md 의 근거를 옮긴다)
```

## EXPLAIN.md (제출 뒤 코드 설명서)

```
# pN 코드 설명서

## 한눈에 보기       (프로그램이 하는 일을 5줄 이내로. 자료 흐름 그림)
## 자료구조          (각 struct, map 이 무엇을 담고 왜 그것을 골랐는지)
## 함수별 설명       (위에서 아래로. 함수마다: 하는 일, 입력과 출력, 눈여겨볼 줄)
## 처음 보는 문법    (이 코드에 나온 문법 중 `/explain` 의 목록에 없는 것. 한 줄 설명과 3줄 예)
## 예제 따라가기     (예제 입력 한 줄씩, 어떤 함수를 거쳐 어떤 출력이 나오는지)
## 결정과 그 이유    (DECISIONS 를 풀어서)
## 예상 질문과 답    (코드를 설명할 때 받을 만한 질문 8~10개. 왜 이 자료구조인가, 어디가 느린가,
##                    실전이라면 무엇을 바꾸나, 이 입력이 오면 어떻게 되나)
## 직접 해 볼 것     (코드를 조금 고쳐 보는 연습 3개)
```
